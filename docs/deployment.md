# Deployment Runbook

This site deploys to Cloudflare Workers through OpenNext. Use this runbook when validating a release locally, previewing the Cloudflare runtime, or deploying production intentionally.

## Architecture

The deployment path has four stages:

1. `scripts/generate-posts-data.ts` reads MDX files in `blog/` and generates `src/lib/posts.data.ts`.
2. Next.js builds the application and pre-renders routes into `.next/`.
3. `@opennextjs/cloudflare` adapts the Next.js build for Cloudflare Workers and writes deployment artifacts to `.open-next/`.
4. Wrangler uses `wrangler.jsonc` to preview or deploy the Worker.

Important files and outputs:

| Path | Purpose |
|---|---|
| `package.json` | Defines local development, build, preview, deploy, and type generation scripts. |
| `open-next.config.ts` | Uses the default OpenNext Cloudflare adapter configuration. |
| `wrangler.jsonc` | Defines the Worker entrypoint, Worker name, compatibility settings, observability, and static asset binding. |
| `.next/` | Next.js build output. Useful for `next start`, but not the final Worker artifact. |
| `.open-next/worker.js` | Worker entrypoint generated by OpenNext and referenced by Wrangler. |
| `.open-next/assets` | Static asset output bound to the Worker as `ASSETS`. |

The current Cloudflare configuration observed for this repository is:

| Setting | Value |
|---|---|
| Worker service | `official-website` |
| Production hostname | `stbensonimoh.com` |
| Deploy target | Default Wrangler deploy target for the `official-website` Worker. No named Wrangler environments are configured. |
| Static asset binding | `ASSETS` |
| Compatibility date | `2026-03-21` |
| Compatibility flags | `nodejs_compat` |
| Observability | Enabled |
| Worker secrets | None currently configured |
| Last deploy source | Wrangler |

## Script Responsibilities

| Command | What it does | Use it when |
|---|---|---|
| `bun run dev` | Regenerates posts data, then starts the Next.js development server. | You are developing locally with fast reloads. |
| `bun run build` | Regenerates posts data, then runs `next build`. | You need to verify the Next.js application compiles and pre-renders successfully. |
| `bun run start` | Runs `next start` against a completed Next.js build. | You need to inspect the production Next.js server behavior. Do not treat this as a Cloudflare Workers runtime check. |
| `bun run preview` | Regenerates posts data, runs `opennextjs-cloudflare build`, then starts a local OpenNext/Cloudflare preview. | You need production-target runtime confidence before deploying. |
| `bun run deploy` | Regenerates posts data, runs `opennextjs-cloudflare build`, then deploys through Wrangler. | You are intentionally deploying production. |
| `bun run cf-typegen` | Runs `wrangler types --env-interface CloudflareEnv cloudflare-env.d.ts`. | Cloudflare bindings change and TypeScript environment types need refreshing. |
| `bun run generate-posts-data` | Regenerates `src/lib/posts.data.ts` from MDX files. | You need to refresh generated post data without running another workflow. |

`bun run start` and `bun run preview` are not interchangeable. `start` runs a local Next.js server from `.next/`; `preview` exercises the OpenNext output that Wrangler serves from `.open-next/`.

## Recommended Validation Paths

Use the narrowest command that answers the question you have.

| Goal | Command |
|---|---|
| Start local development | `bun run dev` |
| Verify the app builds successfully | `bun run build` |
| Verify lint, build, and tests before review | `bun run lint && bun run build && bun run test` |
| Verify deployment-target runtime behavior locally | `bun run preview` |
| Perform an actual production deployment | `bun run deploy` |

Before deploying, run:

```bash
bun run lint
bun run build
bun run test
bun run preview
```

Deploy only after those checks pass and the preview behavior matches expectations:

```bash
bun run deploy
```

## Local Development

Install dependencies once:

```bash
bun install
```

Start the development server:

```bash
bun run dev
```

Open `http://localhost:3000`.

The development server is the fastest way to work on pages, components, content, and styling. It is not a Cloudflare Workers runtime simulation.

## Production-Style Builds

Run a production Next.js build:

```bash
bun run build
```

This validates that Next.js can compile, fetch build-time resources such as fonts, generate static routes, and produce `.next/`. It does not validate the final Cloudflare Worker artifact.

To inspect the resulting Next.js server locally, run:

```bash
bun run start
```

Use `start` only for Next.js production server checks. Cloudflare-specific behavior still needs `preview`.

## Cloudflare Preview

Run a local OpenNext/Cloudflare preview:

```bash
bun run preview
```

This command builds the OpenNext output and serves it through the local Cloudflare preview path. Use it to catch issues caused by Worker runtime differences, asset binding behavior, or `.open-next/` output differences.

Cloudflare preview and production deployment artifacts are generated under `.open-next/`, which is ignored by Git.

## Deployment

Deploy production intentionally:

```bash
bun run deploy
```

This command rebuilds the OpenNext artifact before deploying. Wrangler reads `wrangler.jsonc`, deploys `.open-next/worker.js`, and attaches `.open-next/assets` through the `ASSETS` binding.

After deployment, verify the production hostname:

```bash
curl -I https://stbensonimoh.com/
```

If production behavior regresses, use Cloudflare Workers deployment history to inspect or roll back the `official-website` Worker.

## Deployment Authentication

Deployment requires two environment variables set in the local shell or ignored `.env` file:

| Variable | Required | Purpose |
|---|---|---|
| `CLOUDFLARE_API_TOKEN` | Required for deploy | API token with Workers edit permissions. |
| `CLOUDFLARE_ACCOUNT_ID` | Required for deploy | `104b0d461c72599532997388ee8bd8df`. Setting this explicitly avoids a `/memberships` API call that may not be permitted by the token scope. |

Without `CLOUDFLARE_ACCOUNT_ID`, Wrangler attempts to resolve the account via `/memberships`, which fails with error code `9106` if the API token lacks Account Memberships permissions.

## Environment And Secrets

This project uses three different environments where variables must be set. A `NEXT_PUBLIC_*` value must be present in **every** environment that runs `next build` or `opennextjs-cloudflare build`, because Next.js inlines these into the client JS bundle at build time. They cannot be added after the build.

| Environment | Where to set variables | Used for |
|---|---|---|
| Local development | Ignored `.env` or `.env.local` file | `bun run dev`, `bun run build`, `bun run preview`, `bun run deploy` from your machine. |
| GitHub Actions CI | Repository variables (`vars`) and secrets (`secrets`) | CI workflows that build or validate the application. |
| Cloudflare Git-connected builds | Cloudflare dashboard → Worker Settings → Build → Variables and secrets | Automatic builds triggered by pushes to `main`. |

### Production public analytics

| Variable | Required | Purpose |
|---|---|---|
| `NEXT_PUBLIC_CLARITY_TRACKING_ID` | Required in production | Enables Microsoft Clarity analytics. |

**Where it must be set:**
1. Local `.env` file (ignored by Git)
2. GitHub repository variable: `vars.NEXT_PUBLIC_CLARITY_TRACKING_ID`
3. Cloudflare dashboard build variable: add as a **Variable** (not Secret) under Build → Variables and secrets

### Rules for environment values

- Public client-visible variables must use the `NEXT_PUBLIC_` prefix.
- `NEXT_PUBLIC_*` values are build-time public values. Do not store them only as Cloudflare Worker runtime secrets, because the client bundle is produced before Wrangler deploys the Worker.
- Do not commit `.env`, `.env.local`, `.env.production`, `.dev.vars`, or generated Cloudflare type files.
- Store production-only secrets in Cloudflare or GitHub Actions secrets, not in repository files.
- Keep local-only values in ignored files such as `.env.local` or `.dev.vars`.
- Set public `NEXT_PUBLIC_*` values as GitHub repository variables (`vars`) so CI builds can inline them. Use GitHub Actions secrets (`secrets`) only for actual secrets that must not be visible in build logs.
- For Git-connected Cloudflare Workers builds, add build variables through the Cloudflare dashboard. The build environment is separate from the Worker runtime environment.

Current Cloudflare API inspection shows no Worker runtime secrets configured for `official-website`. If server-side secrets are added later, document the secret names and how to rotate them without including secret values.

## CI Relationship

The CI workflow runs lint, build, and tests on pull requests to `main`:

```bash
bun run lint
bun run build
bun run test
```

On pushes to `main`, CI also validates the OpenNext/Cloudflare packaging path with `opennextjs-cloudflare build`. This packaging validation does not deploy.

## Troubleshooting

### `bun run build` passes but `bun run preview` fails

The Next.js build and Cloudflare Worker artifact are different outputs. Inspect the OpenNext build output and `wrangler.jsonc`, then rerun `bun run preview`. Issues here often involve Worker runtime compatibility, generated `.open-next/` files, or asset binding assumptions.

### `bun run start` works but production behaves differently

`bun run start` runs a Next.js server from `.next/`; production runs a Cloudflare Worker generated under `.open-next/`. Reproduce with `bun run preview` before debugging production-only behavior.

### Missing environment variables

Confirm local variables exist in ignored local files and production values exist in Cloudflare or GitHub Actions as appropriate. Do not add secrets to committed files.

### Cloudflare output confusion

Use `.next/` for Next.js build inspection and `.open-next/` for Cloudflare Worker inspection. Deployment uses `.open-next/worker.js` and `.open-next/assets`, not `.next/` directly.

### Wrangler compatibility date warning during preview

If preview warns that the installed Cloudflare Workers Runtime supports an older compatibility date than `wrangler.jsonc` requests, update Wrangler and rerun `bun run preview`. The preview may start with a fallback compatibility date, but features tied to the newer date may not be available until Wrangler is updated.

### Deploy command updates production unexpectedly

`bun run deploy` is production-oriented. Use `bun run preview` for local runtime validation and reserve `deploy` for intentional production releases.
